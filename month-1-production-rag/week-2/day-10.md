# Day 10 — The probe set — 30 questions with known answers

**Week 2 · Apply · 60 min (light)** · Month 1 — Production RAG

## Objective
Write a 30-question probe set (question + source page + expected chunk) and score all four chunking configs on Recall@5/@10 — verified by a results table generated by script from the set, not scored by hand.

## Why this exists
This small set is the Week 2 judge and the seed of Week 4's golden set. Its discipline — every question carries its expected source — is what separates measurement from demo. Light Friday by design: the thinking is the work today, the runs are short.

## Retrieval warm-up (closed-book, 8–12 min)
1. **Yesterday (Day 9):** state its objective and its verification in one sentence each — from memory, guide closed.
2. **3 days ago (Day 7):** one generative item — write the key command, schema, or rule from that day without looking.
3. **7 days ago (Day 3):** one interleaved item from that day, mixed unlabelled with the others — discrimination between similar ideas is the point.
4. **Prediction:** predict the output/behaviour of today's first build step before you run it. Write the prediction down.
5. Tag every answer with a confidence (0–100%) *before* checking. Answers + one-line explanations come after all attempts — a miss on a prerequisite for today changes today's plan now, per the opening routine.

## Prerequisite check
Re-run Day 9's independent verification ("Chunking — four configurations, one index design") before starting. If it no longer passes, the environment has rotted — repair it first and compress today's objective; do not stack new work on a broken base.

## Core concept
**Direct instruction (short):** Recall@k = 'is the expected chunk in the top k results?' — a retrieval-only metric, no generation involved, no judge to argue with. Question mix mirrors the corpus: factoid, how-to, config/YAML, troubleshooting. Write questions whose answers you can verify against the pinned docs yourself — your domain knowledge is why this corpus was chosen.

## Build steps
Expected output is stated *before* you run each step. If you see something else, stop and check the failure table below.

### Step 1 — Write the 30 questions
~12 factoid, ~8 how-to, ~6 config/YAML, ~4 troubleshooting. Each row: question, source page, expected chunk ID (from config A's indexing), category. Include your 5 from last night.

**Expected output:** 30 rows committed as `evals/probe-v1.jsonl`. Every row's expected chunk verified to exist — by script.

### Step 2 — Build the scorer
Script: embed the question, vector-search the index, check expected chunk in top 5 / top 10. Output per-config CSV. No LLM anywhere in this loop.

**Expected output:** Scorer runs end-to-end on config A and prints a Recall@5/@10 pair.

### Step 3 — Score configs B, C, D
Re-embed/re-index per config (scripted, timed, cost-logged), run the same scorer, same questions, same k.

**Expected output:** 4×2 results table complete. Total experiment spend for the day recorded (target: the whole matrix for well under $1 of embeddings).

### Step 4 — Grade yesterday's prediction
Compare your Day 9 ranking to the measured one. Write 3 sentences on the biggest surprise.

**Expected output:** The surprise paragraph exists. It — not the table — is what you'll remember in Month 3.

## Common failure modes

| Symptom | Cause | Fix |
|---|---|---|
| A question's expected chunk doesn't exist in some config | Chunk boundaries differ per config — expected IDs are config-specific | Map expected *document + section* per config, not raw chunk ID; fixed when the scorer treats all configs fairly by construction |
| Recall = 1.0 everywhere | Probe set too easy / memorised phrasing copied from headings | Rewrite the saturated questions in user language (how someone would actually ask); fixed when the set discriminates between configs |
| Scorer disagrees with a hand check | Scorer bug vs index reality — hand-check 3 questions in the portal/SDK | Reconcile one case fully before trusting any number; fixed when hand and script agree 3/3 |

## Independent verification (checkpoint)
Re-run the scorer from a clean shell: the table regenerates identically. Then hand-verify 3 random rows against the live index. Script + spot-check is the standard for every eval in this course.

## Unaided probe (closed-guide)
State your confidence (0–100%) before checking each answer.

1. Generative recall: define Recall@5 in one sentence and state what it cannot tell you.
2. Transfer: which category (factoid/how-to/YAML/troubleshooting) gained most from heading-aware chunking, per your table — and what's the mechanism?
3. Calibration: how confident were you in yesterday's ranking (0–100%)? Score the ranking honestly against the table and log the gap.
