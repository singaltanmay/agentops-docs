# Coding reps II — DSA refresh at senior-SWE level

**Week 2 · Build · 75 min** · Month 6 — Interview Phase

## Objective
Run the senior-level DSA refresh set (graphs/traversal, intervals, heaps/top-k, sliding window, binary search on answers) as timed reps — the level big-tech loops still gate on, weighted below the production reps deliberately.

## Why this exists
The plan's stance (from the jobs research): DSA is a gate to pass, not the differentiator — refresh to fluency, don't re-live LeetCode season. These five patterns cover the overwhelming majority of senior screens.

## Prerequisites
Lesson 2's gap log reviewed (it opens this lesson's warm-up).

## Retrieval warm-up (closed-book, 8–12 min)
1. **Previous lesson (Month 6 Week 2, Lesson 3 (Live trace-debugging drill — diagnose an agent from its trace)):** state its objective and its verification in one sentence each — from memory, guide closed.
2. **Spaced review (Month 6 Week 1):** one generative item — write the key command, schema, or rule from that lesson without looking.
3. **Interleaved discrimination:** one item mixing this week's pattern with its most confusable neighbour, unlabelled — name which is which and why.
4. **Prediction:** predict the output/behaviour of today's first build step before you run it. Write the prediction down.
5. Tag every answer with a confidence (0–100%) *before* checking. A miss on a prerequisite for today changes today's plan now, per the opening routine.

## Prerequisite check
Re-run the previous lesson's independent verification (Month 6 Week 2, Lesson 3 (Live trace-debugging drill — diagnose an agent from its trace)) before starting. If it no longer passes, repair first and compress today's objective — never stack new work on a broken base.

## Core concept
Rep selection: one problem per pattern, medium-hard, 20 min each for two + rapid-fire pattern-recognition for the rest (given a problem statement, name the pattern + the invariant in 2 minutes — recognition speed is the actual interview skill at senior level).

## Build steps
Expected output is stated *before* you run each step. If you see something else, stop, classify the error (slip / execution-model / API misconception / design misconception), and check the failure notes.

### Step 1 — Pattern-recognition sprint
8 problem statements; name pattern + key invariant for each, 2 min each.

**Expected output:** ≥6/8 patterns named correctly with a workable invariant.

### Step 2 — Timed rep: graph/traversal
One problem (e.g. dependency-order / reachability flavour), 20 min, unaided.

**Expected output:** Solution + complexity stated; edge cases narrated.

### Step 3 — Timed rep: heap/top-k or intervals
One problem, 20 min.

**Expected output:** Solution + complexity; self-review vs the rep rubric.

### Step 4 — Gap log update
Add today's gaps; mark any Lesson 2 gap that today's reps show closed.

**Expected output:** Gap log current; closures require evidence (a passed rep), not feelings.

## Independent verification (checkpoint)
Pattern recognition ≥6/8 and two timed reps with self-reviews recorded; the gap log is current and evidence-based.

## Unaided probe (closed-guide)
State your confidence (0–100%) before checking each answer.

1. Generative: the five patterns with their tell-tale problem shapes, unaided.
2. Prediction: which pattern is your slowest, and what's the 20-minute repair you'd schedule if a loop were tomorrow?

## Definition of done
- [ ] All build steps completed with expected outputs matched
- [ ] Independent verification passed
- [ ] Unaided probe: majority correct *with explanations* (else this lesson's KCs are `fragile` — repair scheduled)
- [ ] System left running; checkpoint committed
- [ ] Log entry written (below) and PROGRESS.md updated

Write your own 3 lines — *what I built / what broke and why / what I still can't do unaided* — then set this lesson's status in PROGRESS.md (`assisted` if any step was demonstrated for you, `mastered` only when the probe passed unaided).
